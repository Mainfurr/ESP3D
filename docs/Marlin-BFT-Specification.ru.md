# Marlin Binary File Transfer: спецификация для реализации

Дата анализа: 2026-09-16. Базовая ревизия репозитория: `250a3ed74eb2a29da3764428bf09f3a69c191c69`.

Документ описывает **Marlin Binary File Transfer (BFT), транспорт 0.1.0 и файловый протокол 0.1.0**, по исходникам данной рабочей копии. Это спецификация совместимости с существующим кодом, а не обещание поведения всех версий Marlin. Рабочее дерево содержит пользовательские изменения, в том числе в конфигурации, очереди G-code и MKS WiFi. Файлы `binary_stream.h/.cpp` и `MarlinBinaryProtocol.py` на момент анализа не изменены относительно HEAD.

«Должен» ниже означает требование к новому совместимому клиенту. Особенности и дефекты текущей прошивки выделены отдельно: их следует учитывать при взаимодействии, но не воспроизводить намеренно в новой реализации приёмника.

### 1.1. Отличие от MKS WiFi

В рабочем дереве также есть [`wifi_module.cpp`](../Marlin/src/lcd/extui/mks_ui/wifi_module.cpp): отдельный протокол MKS ESP с кадром `A5 | type | length_le16 | payload | FC`. Он **не совместим** с описанным здесь BFT. У BFT стартовые байты `AD B5`, Fletcher-16 и текстовые ответы.

Локальный адаптер MKS при включённом `MKS_WIFI_MODULE` обслуживает выделенный `SERIAL_PORT_2`, который исключается из обычного G-code-парсера. Для BFT нужен обычный serial-порт Marlin либо прозрачный канал, передающий все байты без изменений. Поддержка MKS кадрирования в ESP сама по себе не даёт поддержки BFT.

## 2. Назначение и границы возможностей

BFT передаёт файл **от хоста к носителю принтера** через последовательный поток байтов. Данные могут быть произвольными: G-code, изображение, firmware-файл и т. п. Расширение файла не является частью протокола.

Возможности: открыть один файл, последовательно записать блоки, закрыть файл, прервать передачу, использовать heatshrink, провести пробную передачу без записи.

В протоколе отсутствуют:

- скачивание, чтение, listing, rename, mkdir и seek;
- идентификатор файла/транзакции, смещение блока и возобновление с произвольной позиции;
- объявление размера файла, итоговый CRC/hash, проверка свободного места;
- отдельный положительный ответ о завершении каждого `WRITE` на носитель;
- атомарная замена файла, rollback прежнего содержимого и проверка подписи;
- переговоры о baud rate, аутентификация и шифрование.

Загрузка firmware через BFT означает запись файла. Его последующее применение загрузчиком, перезапуск и выбор имени — отдельная, зависящая от платы процедура. `CUSTOM_FIRMWARE_UPLOAD` для обычной передачи файла не требуется.

## 3. Требования к конфигурации и каналу

В прошивке необходимы поддержка носителя и `BINARY_FILE_TRANSFER`; `SDCARD_READONLY` несовместим с этой функцией. `HAS_MEATPACK` одновременно с BFT запрещён `SanityCheck.h`.

Фактические настройки рабочей копии:

| Настройка | Значение |
| --- | --- |
| Плата | `BOARD_BTT_SKR_MINI_E3_V2_0` |
| `SDSUPPORT`, `BINARY_FILE_TRANSFER` | Включены |
| `SERIAL_PORT`, `BAUDRATE` | `-1`, `115200` |
| `SERIAL_PORT_2`, `BAUDRATE_2` | `2`, `115200` |
| `MAX_CMD_SIZE` | `96` |
| `RX_BUFFER_SIZE` | `2048` |
| `LONG_FILENAME_HOST_SUPPORT`, `LONG_FILENAME_WRITE_SUPPORT` | Включены |
| `MKS_WIFI_MODULE`, `SERIAL_XON_XOFF` | Закомментированы |
| `EMERGENCY_PARSER` | Включён |

Это значения исходной конфигурации, не результат проверки установленной на принтере прошивки. Размер payload определяется ответом `ss`, а не размером UART RX-буфера. При этих настройках ожидается максимум **96 байт payload**, то есть **106 байт полного пакета с данными**.

Канал должен сохранять все значения `00..FF`. Нельзя применять преобразование переводов строк, UTF-8-кодирование к бинарным пакетам, G-code line numbering/checksum, MEATPACK или произвольное экранирование. UART-профиль типового клиента — 8N1 на настроенной скорости; конкретный USB CDC backend может иначе трактовать baud rate. Обработка XON/XOFF допустима только если она согласована с конкретной прошивкой; нельзя включать её в ОС по умолчанию для произвольного бинарного канала.

Пакет может приходить частями; границы вызовов `read()`/`write()` не являются границами пакетов. Клиент должен обрабатывать частичную запись в serial-драйвер. Рекомендуемый режим — **один неподтверждённый пакет**, без конвейерной отправки.

Одна файловая передача общая для всей прошивки: поля `SDFileTransferProtocol` статические. Хотя транспортные состояния хранятся по портам, `card.flag.binary_mode` и выбранный `transfer_port_index` глобальны. В бинарном режиме `get_serial_commands()` обслуживает выбранный BFT-порт и возвращается до обычного разбора остальных портов. Это не режим одновременной работы нескольких независимых хостов.

## 4. Вход в бинарный режим и обнаружение

1. Получить монопольный доступ к каналу, дождаться завершения ранее отправленных G-code-команд. Передачу следует начинать при отсутствии печати: открытие файла вызывает `abortFilePrintNow()`.
2. В ASCII-режиме отправить `M115\n` и разобрать ответ до обычного G-code `ok`.
3. При включённом `EXTENDED_CAPABILITIES_REPORT` искать `Cap:BINARY_FILE_TRANSFER:1`; `:0` означает отсутствие поддержки. Отсутствие строки само по себе не доказывает отсутствие BFT: отчёт может быть выключен. Также полезны `Cap:SD_WRITE:1`, `Cap:LFN_WRITE:1`.
4. Остановить фоновые команды клиента и, по возможности, автопериодические отчёты. Ответы диагностик всё равно следует уметь пропускать.
5. Отправить ASCII `M28 B1\n` (штатный Python-клиент использует равнозначное `M28B1\n`). Имя файла здесь не передаётся.
6. Дождаться `echo:Switching to Binary Protocol` и завершения ответа на ASCII-команду. Обычный `ok` может содержать дополнительные поля при `ADVANCED_OK`; он не является бинарным `ok<number>`.
7. Отправить бинарный `CONTROL/SYNC`, получить `ss...`, затем `FILE/QUERY`.

Параметр `B1` должен находиться в начале строкового аргумента M28. Текущий обработчик проверяет буквально `B` и следующую цифру; клиент должен пользоваться каноническим `B1`, не расширять синтаксис до произвольного boolean.

Нельзя приклеивать бинарные данные к ASCII-команде и отправлять их до фактического переключения: обычная очередь ещё может попытаться разобрать их как текст. После входа не отправлять ASCII `M29`, `M28 B0`, `M105` и т. п. Для выхода предназначен бинарный `CONTROL/CLOSE`.

## 5. Формат пакета host → Marlin

Все целочисленные поля шириной более одного байта передаются **little-endian**. Битовые поля protocol/type находятся в одном байте и не зависят от C/C++ bitfield layout.

| Смещение | Размер | Поле | Значение |
| --- | --- | --- | --- |
| 0 | 2 | `token` | `0xB5AD`, на линии `AD B5` |
| 2 | 1 | `sync` | Номер пакета `0..255` |
| 3 | 1 | `meta` | `(protocol_id << 4) | packet_type` |
| 4 | 2 | `length` | Число байт только payload |
| 6 | 2 | `header_checksum` | Fletcher-16 байтов со смещениями 2..5 |
| 8 | `length` | `payload` | Присутствует при `length > 0` |
| `8 + length` | 2 | `packet_checksum` | Только при `length > 0`; Fletcher-16 байтов 2..`7+length` |

Длина полного пакета:

```text
length == 0: 8 байт, footer отсутствует
length >  0: length + 10 байт
```

Полная checksum включает **оба байта header_checksum в порядке передачи**, но не стартовый token и не сам footer. Строкового терминатора после пакета нет. `AD B5` внутри payload не экранируется и при нормальном приёме обрабатывается как обычные данные.

`length` ограничен 16 битами и объявленным в `ss` буфером. Клиент должен проверять размер до отправки. При превышении буфера прошивка не отклоняет заголовок заранее: ошибка возникает во время приёма лишнего байта и приводит к `fe`.

### 5.1. Fletcher-16

Начальные суммы равны нулю. Для каждого байта `b`:

```text
s1 = (s1 + b) mod 255
s2 = (s2 + s1) mod 255
checksum = (s2 << 8) | s1
```

В checksum-поле первым записывается `s1`, затем `s2`. Это не CRC-16 и не сумма modulo 256. Для footer можно заново посчитать checksum указанного диапазона либо продолжить состояние после header, включая байты его checksum.

### 5.2. Минимальный код упаковки

```python
def fletcher16(data: bytes) -> int:
    s1 = s2 = 0
    for b in data:
        s1 = (s1 + b) % 255
        s2 = (s2 + s1) % 255
    return (s2 << 8) | s1


def encode_packet(sync: int, protocol: int, kind: int,
                  payload: bytes = b"", max_payload: int = 96) -> bytes:
    if not 0 <= sync <= 255:
        raise ValueError("sync")
    if not (0 <= protocol <= 15 and 0 <= kind <= 15):
        raise ValueError("protocol/type")
    if len(payload) > min(max_payload, 65535):
        raise ValueError("payload too large")
    header = bytes([sync, (protocol << 4) | kind])
    header += len(payload).to_bytes(2, "little")
    body = header + fletcher16(header).to_bytes(2, "little")
    if payload:
        body += payload
        body += fletcher16(body).to_bytes(2, "little")
    return b"\xAD\xB5" + body
```

Значение `96` здесь только начальный пример. После `SYNC` передавать фактически объявленный `max_payload`. Для начального `SYNC` payload пустой, поэтому размер пока знать не нужно.

## 6. Формат ответов Marlin → host

Ответы **текстовые**, даже в бинарном режиме. `SERIAL_EOL()` завершает строку байтом LF (`0A`). Клиенту полезно принимать и CRLF, удаляя только терминатор. Целые числа в ответах десятичные без обязательных ведущих нулей.

| Строка | Значение |
| --- | --- |
| `ok<n>` | Транспорт принял пакет `n`; при нормальном приёме checksum проверена, операция будет вызвана после ACK |
| `rs<n>` | Требуется пакет с **ожидаемым** номером `n` |
| `ss<n>,<max_payload>,<major>.<minor>.<patch>` | Результат SYNC: следующий ожидаемый номер и возможности транспорта |
| `fe<n>` | Фатальная ошибка транспортного парсера; его sync сброшен в 0 |
| `PFT:version:...:compression:...` | Возможности файлового протокола |
| `PFT:success` | Успех OPEN, CLOSE или ABORT в пределах гарантий обработчика |
| `PFT:fail` | Неудачный OPEN |
| `PFT:busy` | Уже есть активная файловая передача |
| `PFT:invalid` | WRITE/CLOSE без активной передачи |
| `PFT:ioerror` | Ошибка записи, которую обнаружил файловый обработчик |
| `PTF:invalid` | Именно такое написание выдаётся для неизвестного файлового типа: опечатка в прошивке |

`ok`, `rs`, `ss`, `fe` не имеют разделителя перед номером. Для ACK подходит строгий шаблон `^ok([0-9]{1,3})$` с последующей проверкой диапазона `0..255`. Нельзя принимать обычный ASCII `ok`, `ok T:...` или `echo:...ok...` за BFT ACK.

Дополнительно возможны `echo:...`, сообщения SD-карты, автотелеметрия и другие строки. Нужен один постоянный reader с буферизацией неполных строк, классификацией и очередями событий. Нельзя очищать serial input после каждого ACK: непосредственно за ним может стоять результат операции или ошибка.

У ответов нет checksum, transaction ID и номера файловой операции. Повреждение либо потеря строки `PFT:*` может оставить результат операции неопределённым. Неизвестные строки сохранять как диагностику, а не считать успешным завершением.

## 7. Нумерация, подтверждения и повтор

Обозначим `E` — ожидаемый прошивкой номер, `S` — номер входящего пакета.

### 7.1. Нормальный обмен

- После запуска глобально обнуленного экземпляра `E = 0`.
- `SYNC` сообщает текущее `E`, **не устанавливает его равным номеру SYNC** и не увеличивает.
- Новый обычный пакет должен иметь `S = E`.
- При корректном пакете прошивка сначала делает `E = (E + 1) mod 256`, сбрасывает счётчик retries, отправляет `ok<S>`, затем вызывает обработчик операции.
- Клиент после своего `ok<S>` увеличивает локальный номер один раз. `PFT:fail`, `busy`, `invalid` или `ioerror` не откатывают номер: транспорт уже принял пакет.
- Неизвестные protocol/type также могут получить ACK и занять номер, хотя полезное действие не выполнено.
- `M28 B1` и `CONTROL/CLOSE` не обнуляют sync. Повторное соединение должно начинаться с SYNC.

### 7.2. Retransmit

При таймауте ACK отправлять **тот же сохранённый пакет с тем же номером и payload**, а не строить новый WRITE со следующим номером. По `rs<n>`:

- если `n` совпадает с номером текущего неподтверждённого пакета, повторить его;
- если номер отличается, остановить новые WRITE и выполнить восстановление синхронизации; нельзя просто перенумеровать текущие данные и продолжить;
- `rs` не означает успех и не увеличивает номер.

Текущий приёмник распознаёт непосредственный дубликат по условию `S == E - 1`, повторно отправляет `ok<S>` и **не вызывает операцию повторно**. При этом он проверяет только header и сразу переходит к поиску нового token: payload/footer дубликата не поглощаются по длине и не проверяются. Они оказываются мусором в поисковом автомате. Встроенный `AD B5` может запустить ложный разбор заголовка. Это существенное ограничение надёжности повторов произвольных бинарных данных.

Есть ошибка на переходе через 255: при `E = 0` выражение `E - 1` после integer promotion равно `-1`, поэтому повтор `S = 255` не распознаётся. Если `ok255` потерян, обычный повтор может получить `rs0`; при уже ненулевом счётчике retries — быть молча отброшен. Нормальная последовательность `254, 255, 0, 1` без потери ACK работает.

Клиент должен иметь ограничение числа повторов и общего времени операции. Для проблем на wraparound допустим диагностический SYNC: `ss0,...` после отправленного 255 совместим с тем, что транспорт его принял. Это **не** доказывает успешность записи или сохранность потерянного `PFT:ioerror`. Без внешней проверки нельзя объявлять такую передачу безусловно успешной.

### 7.3. Потеря результата файловой операции

ACK всегда предшествует обработке операции. Поэтому:

- Для QUERY, OPEN, CLOSE, ABORT ждать и транспортное подтверждение, и соответствующий результат файлового протокола; хранить их независимо от того, в каком чтении они пришли.
- Повтор с прежним номером может восстановить ACK, но **не повторит `PFT:*`**, даже если исходная строка потерялась.
- QUERY можно заново выполнить с новым номером после установления состояния транспорта: он не пишет файл.
- Повторный OPEN с новым номером не является безопасным универсальным восстановлением: возможны `busy` или повторное создание/усечение файла.
- После потерянного результата CLOSE повторный CLOSE может вернуть `invalid`; это не позволяет доказать предыдущий успех.
- ABORT без уверенности о текущем файле небезопасен для состояния хранилища, см. раздел 9.5.

Для строго надёжного клиента неопределённый файловый результат — отдельное состояние ошибки/требования проверки, а не скрытое успешное завершение.

## 8. Управление соединением: protocol = 0

| type | meta | Команда | Payload | Ответ |
| --- | --- | --- | --- | --- |
| 1 | `01` | SYNC | Нет | Только `ss...`, без `ok` |
| 2 | `02` | CLOSE | Нет | `ok<S>`, затем возврат к ASCII |

### 8.1. SYNC

Пример запроса: `AD B5 00 01 00 00 01 03`.

Пример ответа: `ss0,96,0.1.0\n`.

Любое значение sync в корректном header SYNC принимается. Обработка выполняется сразу после проверки header, ещё до обычной проверки номера и payload. Поэтому SYNC **обязательно отправлять с нулевой длиной**: реализация игнорирует ненулевую длину и не поглощает такое тело как payload.

SYNC не закрывает файл, не сбрасывает heatshrink, не обнуляет счётчик retries и не продлевает файловый таймаут. Им можно узнать состояние транспорта, но нельзя получить состояние файла или позицию записи. Версия транспорта и версия файлового протокола запрашиваются раздельно; совпадение обеих с `0.1.0` не следует превращать в общее правило.

### 8.2. CONTROL/CLOSE

После ACK прошивка устанавливает `card.flag.binary_mode = false`. Она **не закрывает активный файл**, не вызывает ABORT и не сбрасывает sync. Сначала клиент должен завершить FILE/CLOSE либо FILE/ABORT.

Текущий `receive()` после dispatch не прерывается немедленно и может продолжать читать до конца своего временного окна 20 мс. Поэтому нельзя посылать ASCII-команду вплотную вслед за `ok` выхода: она ещё может попасть в бинарный поиск token. Практический клиент должен дать парсеру завершить вызов, например выдержать защитную паузу порядка 50 мс, затем проверить ASCII-режим командой `M115`. Это рекомендация для текущего кода, не дополнительное поле или гарантированный дедлайн протокола.

## 9. Файловый протокол: protocol = 1

| type | meta | Команда | Payload |
| --- | --- | --- | --- |
| 0 | `10` | QUERY | Нет |
| 1 | `11` | OPEN | `dummy:u8`, `compression:u8`, `filename`, `00` |
| 2 | `12` | CLOSE | Нет |
| 3 | `13` | WRITE | Байты файла либо байты единого сжатого потока |
| 4 | `14` | ABORT | Нет |

Для QUERY/CLOSE/ABORT клиент должен отправлять нулевую длину, хотя обработчики не проверяют отсутствие лишних данных. Каждая **обработанная** команда protocol 1, включая неизвестный тип, обновляет файловый дедлайн `millis() + 10000`.

### 9.1. QUERY

Запрос без payload. После ACK возвращает одну из строк:

```text
PFT:version:0.1.0:compression:heatshrink,8,4
PFT:version:0.1.0:compression:none
```

`8` и `4` — число бит окна и lookahead, а не размеры в байтах. Текущий `binary_stream.h` сам определяет `BINARY_STREAM_COMPRESSION`, а `heatshrink_config.h` задаёт `8,4`, поэтому в этой реализации ожидается первая строка. Клиент должен разбирать полученный ответ, а не жёстко задавать алгоритм.

QUERY не резервирует файловый канал и не сообщает, есть ли открытый файл. Его можно использовать как keepalive открытой передачи. Новый QUERY, отправленный после последнего ACK WRITE и полностью обработанный в том же потоке, также служит барьером: предыдущий WRITE уже прошёл dispatch, а его возможная ошибка должна была появиться в потоке раньше ответа QUERY. Такой барьер не восстанавливает потерянные ответы и не является проверкой данных на SD.

### 9.2. OPEN

Payload:

| Смещение внутри payload | Размер | Поле |
| --- | --- | --- |
| 0 | 1 | `dummy`: 0 — писать файл, 1 — пробная передача |
| 1 | 1 | `compression`: 0 — без сжатия, 1 — heatshrink из QUERY |
| 2 | N | Имя/путь файла |
| `2+N` | 1 | Нулевой терминатор |

Итого `length = N + 3`, где N — **байты**, не символы. При буфере 96 максимум имени/пути на транспортном уровне — 93 байта. Ограничения файловой системы могут быть строже.

Текущая валидация проверяет только `length > 2` и последний байт `00`. Пустое имя и внутренний NUL ею не запрещены; реальная работа затем зависит от файловой системы. Новый клиент должен требовать непустое имя и запрещать внутренний NUL. Флаги фактически читаются как `value & 1`; посылать следует только 0 или 1, остальные биты оставить нулевыми.

Штатный Python-клиент кодирует имя UTF-8. Wire-протокол не объявляет encoding, а firmware передаёт байты файловой системе. ASCII-имена DOS 8.3 дают наиболее переносимый вариант. Для длинных имён нужна `LONG_FILENAME_WRITE_SUPPORT`; поддержка их отображения сама по себе недостаточна. Unicode и ограничения FAT следует проверять для выбранной сборки, не выводить их из версии BFT.

При обычном OPEN обработчик выполняет `card.mount()`, затем `card.openFileWrite(filename)`. `mount()` переходит в корень, поэтому для этой реализации относительное имя начинает разрешаться от корня. Можно передавать путь с `/`; каталоги должны уже существовать. `0:/...` и `1:/...` из адаптера MKS не являются синтаксисом BFT. Для базового клиента рекомендуется файл в корне: удаление при ABORT для подкаталогов имеет дефект.

Файл открывается с `O_CREAT | O_APPEND | O_WRITE | O_TRUNC`: существующий файл **усекается**, продолжения прежних данных нет. До этого `openFileWrite()` останавливает текущую файловую печать. Положительный ответ не означает выделения места под весь будущий файл.

Ответы после ACK:

| Ответ | Состояние |
| --- | --- |
| `PFT:success` | Передача активна, можно WRITE |
| `PFT:busy` | Уже установлено `transfer_active`; новая передача не открыта |
| `PFT:fail` | Payload невалиден либо открыть файл не удалось |

`dummy=1` пропускает mount/open/write/close/remove носителя, но выставляет активную передачу, принимает данные и при необходимости распаковывает их. Успех dummy не доказывает доступность SD и допустимость имени файла. На каждый успешный OPEN состояние декодера сбрасывается, буфер распакованных данных обнуляется по длине.

### 9.3. WRITE

Payload записывается последовательно в открытый файл. `length` не превышает объявленный предел. Последний блок может быть короче, обязательного выравнивания нет. Данные не должны изменяться: без преобразования LF/CRLF, без добавления NUL.

Для обычного несжатого файла передаваемые payload в совокупности равны исходному файлу. Для сжатого — это последовательные куски одного heatshrink-потока. Нулевой WRITE не является EOF и не нужен; пустой файл передаётся как OPEN → CLOSE без WRITE.

Положительный ответ — **только транспортный `ok<S>`**. Ошибки после него:

- `PFT:invalid`: нет активной передачи;
- `PFT:ioerror`: ошибка записи, обнаруженная через отрицательный результат `card.write()`.

ACK отправляется **до** вызова записи. Reader должен постоянно проверять ошибки, в том числе после получения ACK и во время ожидания следующего пакета. Нельзя безусловно пометить байты «сохранёнными» по `ok`.

При `ioerror` нет автоматического снятия `transfer_active` и гарантированного отката частично записанного блока. Повторить этот WRITE с новым номером — значит рисковать дублированием части файла и нарушением состояния распаковки. Передачу считать неуспешной, новые данные остановить, затем выполнить контролируемое прекращение своей передачи.

### 9.4. FILE/CLOSE

Без payload. Если активен обычный файл, сбрасывается остаток 512-байтового буфера распакованных данных, вызываются `card.closefile()` и `card.release()`. Затем вызывается `heatshrink_decoder_finish()` и снимается `transfer_active`. Для dummy операции с SD пропускаются.

Ответы после ACK:

- `PFT:success`: обработчик завершил закрытие;
- `PFT:ioerror`: обнаружена ошибка записи остатка буфера; активное состояние при этом сохраняется;
- `PFT:invalid`: активной передачи нет.

Существенные пределы гарантии `success`: результат `heatshrink_decoder_finish()` игнорируется; `CardReader::closefile()` не передаёт наружу результаты `myfile.sync()` и `myfile.close()`. Значит, не все ошибки flush/закрытия и не все случаи усечённого сжатого потока становятся `PFT:ioerror`. Итоговый размер и hash не проверяются.

Это закрывает **файл**, но оставляет транспорт в бинарном режиме. После обычного CLOSE носитель освобождён; для последующей ASCII-работы с ним может потребоваться `M21`. Несколько файлов можно последовательно передать за один бинарный сеанс через новые OPEN/CLOSE.

### 9.5. ABORT

Без payload. Обработчик закрывает текущий файл, вызывает `card.removeFile(card.filename)`, освобождает носитель и снимает активность. Для dummy операции с SD пропускаются. После ACK всегда печатается `PFT:success`.

Важные особенности текущего кода:

- Нет проверки `transfer_active` перед удалением; ABORT без своей активной передачи может попытаться удалить последний выбранный файл, если носитель смонтирован.
- `card.filename` — глобальное выбранное DOS-имя, не сохранённый полный путь транзакции. OPEN пути в подкаталог не меняет workDir через `diveToFile(false, ...)`, а выбор имени делается относительно workDir. Удаление может не попасть в нужный файл либо затронуть одноимённый/ранее выбранный файл. Это вывод из структуры вызовов, требующий отдельной аппаратной проверки для используемой конфигурации SD.
- Возвращаемый результат удаления не проверяется: `PFT:success` не гарантирует фактического удаления. Диагностика SD может сообщить `Deletion failed...`.
- ABORT не восстанавливает содержимое файла, усечённого OPEN.

Новый клиент не должен использовать ABORT как универсальную команду «на всякий случай». При `busy` нельзя автоматически удалять чужую или неидентифицированную передачу. Для своей подтверждённой передачи файл следует открывать под однозначным именем, сохранять этот путь у клиента и отдельно проверять cleanup при ошибках.

## 10. Heatshrink

Сжимать следует файл как **один поток**, завершить кодер штатным способом и затем нарезать выходные байты на WRITE-payload. Потоковый encoder также допустим, если сохраняет историю между WRITE. Нельзя отдельно сжимать каждый блок с новой историей.

Для `heatshrink,8,4`:

- размер окна — `2^8 = 256` байт;
- максимальная длина ссылки — `2^4 = 16` байт;
- в прошивке входной буфер декодера — 32 байта, буфер выхода для SD — 512 байт;
- эти внутренние размеры не заменяют ограничение payload из SYNC;
- распакованный блок может быть больше payload, история сохраняется через границы пакетов.

Базовое битовое представление, установленное по встроенному декодеру:

| Элемент | Биты |
| --- | --- |
| Литерал | `1`, затем 8 бит значения байта |
| Ссылка назад | `0`, затем W бит `(distance - 1)`, затем L бит `(length - 1)` |

Биты читаются от старшего к младшему внутри байта; многобитное значение собирается старшими битами вперёд. Это отдельно от little-endian целых полей BFT. Ссылки допускают перекрывающееся копирование. При reset окно декодера заполняется нулями. Конец потока дополняется нулевыми битами до границы байта, специального BFT EOF или заголовка архива нет.

Предпочтительно использовать совместимый heatshrink encoder, например тот же вызов, что в клиенте репозитория:

```python
compressed = heatshrink.encode(
    source_bytes, window_sz2=window_bits, lookahead_sz2=lookahead_bits
)
```

В OPEN установить `compression=1` только при распознанном алгоритме и поддерживаемых параметрах. Если сжатие недоступно, посылать исходные байты с `compression=0`. Не добавлять gzip/zlib-заголовок, размер исходного файла или свою checksum внутрь сжатого потока.

Checksum BFT защищает **сжатые передаваемые байты**. Сквозной проверки результата распаковки нет. Ошибка обрезания файла/потока, не нарушающая пакеты, может не обнаружиться.

## 11. Таймауты и конечный автомат приёмника

| Параметр | Текущий код | Смысл |
| --- | --- | --- |
| `packet_max_wait` | 500 мс | Максимальный перерыв между читаемыми байтами начатого пакета |
| `rx_timeslice` | 20 мс | Плановое окно обработки за один вызов receive; не ACK SLA |
| `max_retries` | 0 | Неограниченные запросы повторов |
| `packet_retries` | `uint8_t` | После 255 запросов переполняется |
| Файловый `timeout` | 10000 мс | Дедлайн после последней обработанной команды protocol 1 |
| Файловый `idle_period` | 1000 мс | Период проверки просроченной передачи во время idle |
| Таймаут ответа типового upload-клиента | 1000 мс | Параметр клиента, не правило wire-протокола |
| Общий timeout `Protocol.send()` | `response_timeout * 20` | Ограничение ожидания в Python-примере |

500 мс — не общая длительность пакета. Таймер продлевается каждым прочитанным байтом. Пока парсер ищет token (`PACKET_WAIT`), транспортного таймаута нет. Внешнему клиенту следует иметь собственный монотонный таймер, учитывать длительность записи блока и задержки SD и не делать пауз внутри пакета.

Автомат:

```text
RESET → WAIT_TOKEN → HEADER → DATA → FOOTER → PROCESS → RESET
                         └── length=0 ────────┘

HEADER + valid SYNC → ss... → RESET
HEADER + previous sync → ok... → RESET (особенности дубликатов: раздел 7)
bad checksum / wrong sync / starvation → RESEND → rs<E> → RESET
payload buffer overflow / exhausted retries → ERROR → fe<S> → reset sync=0
```

На старте HEADER сначала проверяется checksum. Для правильного, но неожиданного номера при ненулевом `packet_retries` кадр может быть отброшен **без ответа**; при нулевом счётчике выдаётся resend. Неизвестные протоколы доходят до dispatch после ACK.

Фатальная ошибка сбрасывает транспортный sync, retries и индекс буфера, но **не выходит из binary mode и не закрывает файл**. Требуется повторный SYNC, а затем отдельное решение о прекращении своей файловой передачи.

Диагностические строки транспорта (префикс `echo:` добавляет `SERIAL_ECHO_MSG`):

| Текст после `echo:` | Причина / последующее действие |
| --- | --- |
| `Datastream packet out of order` | Неожиданный sync, переход к resend |
| `Packet header(<S>?) corrupt` | Неверная header checksum; значение S могло быть повреждено |
| `Packet(<S>) payload corrupt` | Неверная полная checksum, переход к resend |
| `Datastream packet data buffer overrun` | Превышен буфер, переход к fatal error |
| `Datastream timeout` | Истёк межбайтовый таймаут, переход к resend |
| `Resend request <retry_count>` | Перед строкой `rs<E>`; это счётчик попыток, не номер пакета |
| `Unknown BinaryProtocolControl Packet` | Неизвестный type для protocol 0, уже после ACK |
| `Unsupported Binary Protocol` | Неизвестный protocol ID, уже после ACK |

Клиенту не следует управлять нумерацией по диагностическим строкам: машинные ответы для этого — `ok`, `rs`, `ss`, `fe`.

Файловая проверка idle вызывается только когда `PACKET_WAIT` не находит входных данных. При обычном простое примерно через 10–11 секунд активная передача автоматически прерывается и предпринимается удаление файла. Отдельного `PFT:timeout` или `PFT:success` при этом нет; возможна только диагностика SD. Входящий мусор, незавершённые пакеты и загрузка обработчиков могут задерживать проверку, поэтому это не жёсткая гарантия удаления за 11 секунд.

SYNC, неверные пакеты и дубликаты не продлевают файловый timeout. Для длительной паузы нужен новый FILE/QUERY, например каждые 3–5 секунд, с нормальной обработкой номера и ответа. Следует подготовить/сжать данные до OPEN, чтобы не простаивать с открытым файлом.

Если CONTROL/CLOSE отправлен при активном файле, BFT idle больше не вызывается обычным путём; нельзя рассчитывать, что файловый таймаут затем автоматически выполнит cleanup.

На 8-битных целях есть дополнительный дефект: `transfer_timeout` и `idle_timeout` объявлены как `size_t`, а не `millis_t`. При 16-битном `size_t` значения абсолютного времени усекаются. Указанные 10 секунд нельзя считать переносимой гарантией для AVR без исправления или проверки. Для текущей STM32-платы `size_t` 32-битный.

## 12. Рекомендуемая архитектура клиента

Разделить транспорт последовательного порта, бинарный encoder, reader строк, менеджер номера пакета и файловую транзакцию. Публичный API может иметь операции `enter_binary`, `sync`, `query`, `open`, `write`, `close_file`, `abort_owned_transfer`, `leave_binary`. Отдельно хранить `acknowledged_bytes` и итоговый результат файла: ACK не равен сохранению.

Последовательность успешной передачи:

```text
ASCII_READY
  → M28 B1 и завершение ASCII-ответа
  → SYNC / ss: установить номер и максимум payload
  → QUERY / ACK + возможности
  → подготовить данные и проверить имя
  → OPEN / ACK + PFT:success
  → WRITE / ACK, постоянный контроль PFT-ошибок (повторять)
  → FILE/CLOSE / ACK + PFT:success
  → CONTROL/CLOSE / ACK
  → защитная пауза, проверка ASCII-режима
  → при необходимости M21 и проверка файла
```

Обязательные правила обработки событий:

1. Все команды идут через один диспетчер, который не допускает фоновых ASCII-запросов в BFT.
2. Сохранять исходный пакет до ACK. Не изменять номер и payload при retry.
3. Принять правильный ACK один раз. Повтор уже обработанного ACK не должен ещё раз увеличивать номер. Произвольный неожиданный ACK нельзя считать подтверждением текущего запроса.
4. Обрабатывать `rs`, `ss`, `fe` и `PFT:*` независимо; ошибка приложения может прийти после транспортного завершения `write()`.
5. Для операций с положительным файловым ответом ждать его отдельно. `PFT:success` без текущего подходящего запроса — не основание объявить успех следующей операции.
6. После ошибки WRITE не продолжать файл и не смешивать его ошибки с результатами CLOSE. Если нужна строгая граница перед cleanup, выполнить новый QUERY и дождаться его ответа, сохраняя все предшествующие ошибки.
7. После `busy`, потери OPEN/CLOSE-результата либо рассинхронизации сохранять состояние «неопределённо». Автоматическое удаление/перезапись допустимо только по явно выбранной политике клиента для принадлежащего ему пути.
8. После перезапуска устройства, переподключения USB или потери режима не продолжать передачу с последнего локального смещения. В BFT нет resume.
9. Даже при успешном CLOSE результат формулировать как «передача завершена по протоколу». Для требования побайтовой достоверности нужна внешняя проверка файла либо расширение протокола с размером и hash.

Обычный `M20` после выхода может помочь проверить наличие/размер, если файл отображается выбранным listing-режимом. Это не проверка содержимого; видимость `.bin` и расширенный listing зависят от конфигурации. BFT не предоставляет команду чтения hash.

## 13. Полный пример обмена и контрольные пакеты

Все hex ниже — байты на линии. Начальное ожидаемое значение 0, без сжатия, файл `A.GCO`, содержимое `G28\n` (4 байта). Диагностические строки SD опущены; они допустимы между ACK и `PFT:*`.

```text
host → M28 B1\n
Marlin → echo:Switching to Binary Protocol\n
Marlin → ok\n

host → AD B5 00 01 00 00 01 03                       # CONTROL/SYNC
Marlin → ss0,96,0.1.0\n

host → AD B5 00 10 00 00 10 30                       # FILE/QUERY, sync 0
Marlin → ok0\n
Marlin → PFT:version:0.1.0:compression:heatshrink,8,4\n

host → AD B5 01 11 08 00 1A 47 00 00 41 2E 47 43 4F 00 C4 C6
                                                       # OPEN, sync 1
Marlin → ok1\n
Marlin → PFT:success\n

host → AD B5 02 13 04 00 19 49 47 32 38 0A 37 13       # WRITE, sync 2
Marlin → ok2\n

host → AD B5 03 12 00 00 15 42                       # FILE/CLOSE, sync 3
Marlin → ok3\n
Marlin → PFT:success\n

host → AD B5 04 02 00 00 06 16                       # CONTROL/CLOSE, sync 4
Marlin → ok4\n
```

Машинно-читаемые контрольные пакеты: [`Marlin-BFT-TestVectors.json`](Marlin-BFT-TestVectors.json). Они содержат исходные поля, payload, обе checksum и полный hex. Включены также нулевой payload, крайние номера, максимальный payload 96, все 256 значений байта при гипотетическом большем объявленном буфере и сжатый литерал `A`. Всего 15 корректных пакетов и 4 некорректных случая. Поля `header_checksum`/`packet_checksum` в JSON представляют числовое hex-значение 16-битной суммы; `packet_hex` содержит байты в порядке передачи.

### 13.1. Сценарии для приёмочных проверок будущей реализации

| Сценарий | Ожидаемая проверка |
| --- | --- |
| Начальный SYNC с произвольным номером | Нет ACK; ответ сообщает текущее E, следующий QUERY использует E |
| Второй сеанс без перезагрузки | Не предполагать E=0 |
| Нулевой payload | Только 8 байт, без footer |
| Размер payload = max | Успешный приём; checksum учитывает length little-endian |
| Размер payload > max | Клиент отклоняет до отправки; при тесте прошивки ожидается `fe` при переполнении |
| Произвольные `00`, LF, CR, `AD B5`, `FF` | Без преобразований внутри данных |
| Дробление каждого пакета на однобайтовые reads | То же содержимое, без зависимости от chunk boundaries |
| Несколько строк в одном read, одна строка в нескольких reads | ACK и PFT-результат не теряются |
| Искажённая header checksum | `rs<E>`, данные не должны записаться |
| Искажённый payload/footer | `rs<E>`, dispatch не вызывается |
| Пауза >500 мс внутри пакета | `Datastream timeout`, затем `rs<E>` |
| Потеря ACK | Повтор без двойной записи; отдельно проверить payload с token и потерю `ok255` |
| Нормальный wraparound | Последовательность 254, 255, 0, 1 проходит |
| Потеря `PFT:success` при сохранённом ACK | Клиент не выдаёт ложный успех и не делает слепой повтор открытия |
| Нет SD / нельзя открыть имя | `ok<S>`, затем `PFT:fail` |
| OPEN при активной передаче | `PFT:busy`, существующий файл не менять |
| WRITE/CLOSE без OPEN | `PFT:invalid`, транспортный номер всё равно потреблён |
| Ошибка SD во время WRITE | ACK может предшествовать `ioerror`; клиент прекращает новые WRITE |
| Ошибка окончательного flush | Зафиксировать текущий пробел диагностики, не приравнивать ACK к durability |
| Пустой файл | OPEN → CLOSE, размер 0; клиент не делит на ноль |
| Сжатый файл через несколько WRITE | Единая история, полное совпадение распакованных байтов |
| Остаток распаковки <512 байт | Записывается при FILE/CLOSE |
| Dummy | Нет изменения SD; сжатие и транспорт всё ещё обрабатываются |
| Простой открытого файла | Автоматическое прекращение в idle; проверить отсутствие PFT timeout |
| Keepalive | FILE/QUERY продлевает дедлайн, CONTROL/SYNC — нет |
| Выход из binary | FILE/CLOSE перед CONTROL/CLOSE, последующий ASCII после завершения парсера |
| Подкаталоги / ABORT без передачи | Проверять только на тестовом носителе с учётом дефекта выбора удаляемого файла |

## 14. Требования к новой реализации приёмника

Если планируется не только клиент, но и собственный совместимый сервер/firmware, сохранить wire-формат, номера типов, ASCII-ответы, порядок ACK перед файловым результатом и семантику SYNC. Для исправлений, не требующих новых полей, следует:

- сравнивать предыдущий номер через явное приведение `uint8_t(E - 1)`;
- полностью поглощать payload/footer дубликата, не сканировать их как новый поток;
- валидировать размер, допустимый тип и структуру payload до побочных эффектов;
- хранить полный путь принадлежащего транзакции файла и проверять активность перед ABORT;
- проверять число записанных байт и результаты sync/close/remove/decoder finish;
- использовать `millis_t` для дедлайнов;
- прекращать binary receive сразу после CONTROL/CLOSE;
- исключить разбор произвольных бинарных данных emergency-парсером на всём протяжении сеанса;
- ограничивать бесконечное ожидание/повторы и однозначно публиковать ошибку.

Кэширование файлового результата для повторной отправки, новое подтверждение записи, итоговый hash/размер и возобновление — уже расширения наблюдаемого протокола. Для них нужна явная версия/negotiation и отдельная спецификация; нельзя молча добавлять footer, типы или ответы в ожидании, что старый клиент их поймёт.

## 15. Расхождения документации и ограничения эталонного Python-клиента

| Место | Наблюдаемая проблема | Следствие для новой реализации |
| --- | --- | --- |
| Старое описание `rs` | Назван «последний принятый номер», код передаёт текущий ожидаемый `sync` | Использовать ожидаемый номер, не прибавлять 1 |
| Старое описание ACK | Говорит только о правильном header | Новый пакет с payload получает ACK после проверки footer; дубликат — только после header |
| Старое описание ABORT | Обещает удаление | Удаление не проверяется, полный путь не хранится |
| Старое описание FILE/CLOSE | Создаёт впечатление полной проверки сохранения | Результаты sync/close и decoder finish не проверяются |
| `FileTransferProtocol.__init__()` | Зарегистрирован `PTF:invalid`, но не `PFT:invalid` | Парсить оба фактически встречающихся написания |
| `FileTransferProtocol.write()` | Ждёт только транспорт, не обрабатывает прикладную ошибку WRITE непосредственно | Постоянно принимать и связывать PFT-ошибки с транзакцией |
| `FileTransferProtocol.copy()` | `filesize / len(data)` падает при пустом несжатом файле | Отдельно поддержать OPEN → CLOSE |
| `FileTransferProtocol.open()` | При `busy` автоматически вызывает ABORT | Не повторять эту политику без владения текущей передачей |
| `Protocol.response_ok()` | Жёстко требует совпадения с текущим sync | Обработать запоздалый дубликат ACK без повторного продвижения номера |
| `Protocol.send_ascii()` | Может считать любой первый зарегистрированный ответ завершением ASCII-запроса | Разделить ASCII-handshake и бинарные ACK |
| `responses`, `applications` | Некоторые mutable-очереди/списки объявлены как атрибуты класса | В новом клиенте хранить на экземпляре соединения |
| `transmit_packet()` | Не проверяет количество байт, возвращённое `port.write()` | Обрабатывать частичную отправку |
| `copy()` при `errors > 0` | Прекращает передачу через CLOSE, может оставить частичный файл | Явно определить cleanup и результат ошибки |

Дополнительная особенность emergency parser: обычный `openFileWrite()` его отключает, `closefile()` включает. `M28 B1` сам его не отключает, а dummy OPEN вообще не вызывает `openFileWrite()`. Следовательно, нельзя считать весь BFT-сеанс автоматически защищённым от распознавания ASCII emergency-последовательностей в произвольных бинарных байтах; поведение также зависит от HAL. Это следует отдельно проверить для целевой платы, особенно для dummy и периода после закрытия файла.

## 16. Что проверено при подготовке

Спецификация получена чтением локальных обработчиков, Python-клиента, CardReader и heatshrink. Алгоритм из раздела 5.2 выполнен как независимый encoder: 15 корректных контрольных пакетов и ещё 1000 воспроизводимых сгенерированных комбинаций полей/payload сопоставлены с методом `Protocol.build_packet()` из репозитория без открытия serial-порта; все совпали. Для некорректных пакетов ожидаемые реакции определены по коду, а не измерены на устройстве. Проверка C++ integer promotion подтверждает описанную проблему дубликата 255. Также проверены JSON, локальные ссылки и соответствие hex-примеров в тексте контрольным пакетам.

Прошивка не изменялась и не прошивалась; физический обмен с принтером, поведение SD при сбоях и работа на AVR не проверялись. Матрица раздела 13.1 предназначена для последующей реализации и аппаратной проверки, а не является заявлением о пройденных испытаниях.
