# OctoPrint API: загрузка файлов через Marlin BFT

ESP3D реализует минимальный совместимый с OctoPrint HTTP API для загрузки
файлов на SD-карту принтера. Это API предназначено для клиентов вроде
PrusaSlicer, которые используют OctoPrint как host.

Файл не сохраняется во flash-файловой системе ESP3D и не буферизуется целиком
в RAM: содержимое multipart-поля потоково передаётся через **Marlin Binary
File Transfer (BFT)** в корень SD-карты принтера.

Реализованы только описанные ниже операции. Это не полный OctoPrint REST API:
нет списка файлов, удаления, выбора файла отдельным запросом, job/status API
и API-ключей OctoPrint.

## Когда маршрут доступен

Маршруты регистрируются, если одновременно выполнены условия:

- включён `HTTP_FEATURE`;
- `COMMUNICATION_PROTOCOL == RAW_SERIAL`;
- целевая платформа — ESP8266 или ESP32.

Принтер должен поддерживать Marlin BFT 0.1.0 и запись на SD. Перед передачей
ESP3D проверяет ответ `M115`, переходит в BFT командой `M28 B1`, синхронизирует
протокол, открывает файл, передаёт данные и корректно закрывает BFT-сеанс.
Если Marlin явно сообщает `Cap:BINARY_FILE_TRANSFER:0` либо `Cap:SD_WRITE:0`,
загрузка завершается ошибкой.

Во время BFT-сеанса UART принтера эксклюзивно занят. Второй upload получает
`409`, а обычные G-code через HTTP/WebSocket отклоняются до окончания либо
контролируемого прерывания текущей передачи.

> Важно: эти два маршрута сейчас не используют обычную проверку HTTP-сессии
> ESP3D. Даже при включённом `AUTHENTICATION_FEATURE` они не требуют cookie,
> Basic auth или OctoPrint API key. Не публикуйте HTTP-порт в недоверенную
> сеть без внешней защиты.

## `GET /api/version`

Возвращает фиксированную версию, достаточную для обнаружения OctoPrint-клиентом.

```http
GET /api/version HTTP/1.1
Host: esp3d.local
```

Успешный ответ всегда имеет HTTP `200`, `Content-Type: application/json`:

```json
{"api":"0.1","server":"1.11.0","text":"OctoPrint 1.11.0"}
```

Это значение совместимости, а не сведения о фактически установленной версии
OctoPrint: на устройстве работает ESP3D.

## `POST /api/files/local`

Принимает один файл в `multipart/form-data` и передаёт его на SD-карту
принтера. Путь `local` — имя области хранения OctoPrint; здесь он означает
корень SD-карты Marlin.

### Запрос

Обязателен `Content-Type: multipart/form-data; boundary=…`. Передавайте также
`Content-Length`; это обязательно для ESP8266 и обеспечивает одинаковое
поведение на обеих платформах. `Transfer-Encoding: chunked` не поддерживается
на ESP8266, поэтому его не следует использовать.

В multipart body должен быть ровно один part:

```http
Content-Disposition: form-data; name="file"; filename="cube.gcode"
Content-Type: application/octet-stream

; G-code bytes follow
```

Требования к `filename`:

- от 1 до 120 байт;
- только имя файла в корне SD — без `/` и `\\`;
- запрещены `: * ? " < > |`, управляющие символы и подстрока `..`;
- запятая в принятом имени заменяется на `_` перед передачей в Marlin.

Для наибольшей совместимости используйте короткое ASCII-имя. Дополнительные
нефайловые multipart-поля игнорируются, кроме `print` и `select`. Повторный
part `file` — ошибка. Поле `select` принимается, но сейчас не меняет состояние
принтера и не отображается в ответе. HTTP-парсер допускает до 120 байт, но
после BFT `SYNC` действует дополнительный лимит Marlin: имя вместе со служебными
тремя байтами должно поместиться в согласованный payload. Например, при
payload 96 байт предельная длина имени — 93 байта.

Если Marlin отвечает `PFT:fail` (в некоторых сборках `PTF:fail`) на открытие
G-code файла с длинным именем, ESP3D повторяет загрузку под постоянным коротким
именем из восьми букв и цифр с расширением `.GCO`. В ответе HTTP и при
автозапуске печати используется это фактическое имя на SD. Если открытие
короткого имени тоже не удалось, загрузка завершается ошибкой.

Поле `print` может иметь значение `1` или `true` (регистр `true` не важен).
После успешного закрытия BFT ESP3D тогда запускает напечатанный файл. Другие
значения означают «не печатать».

Пример `curl` с загрузкой и запуском печати:

```sh
curl --fail-with-body -i \
  -F 'file=@cube.gcode;filename=cube.gcode;type=application/octet-stream' \
  -F 'print=true' \
  http://esp3d.local/api/files/local
```

Пример на Python находится в
[`tools/bft/upload_via_esp3d.py`](../tools/bft/upload_via_esp3d.py). Он
проверяет `/api/version`, формирует streaming multipart-запрос и ожидает
HTTP `201` с `done: true`.

### Успешный ответ

После успешного BFT `CLOSE` сервер возвращает HTTP `201 Created`:

```json
{
  "done": true,
  "files": {
    "local": {
      "name": "cube.gcode",
      "path": "cube.gcode",
      "origin": "local"
    }
  }
}
```

`path` не является URL и не включает `/`; это имя файла в корне SD. Успех
подтверждает принятие и закрытие файла BFT. Отдельная проверка hash или
сравнение содержимого файла на SD API не выполняет.

Если задан `print=true`, после upload ESP3D последовательно выполняет `M21`,
`M23 <filename>` и `M24`, ожидая подтверждение каждой команды. HTTP `201`
означает, что Marlin подтвердил `M24`; это не гарантия начала движения
механики.

### Ошибки

Ошибочный ответ имеет `Content-Type: application/json` и тело вида:

```json
{"error":"описание причины"}
```

| HTTP | Когда возвращается |
| --- | --- |
| `400 Bad Request` | Некорректный multipart/body, нет поля `file`, неверно имя, BFT/Marlin отказал, файл не закрылся либо не удалось запустить печать. |
| `408 Request Timeout` | Только ESP8266: тело не поступало 5 секунд либо весь upload занял 30 минут. |
| `409 Conflict` | Уже идёт другой BFT upload. |

ESP32 использует потоковый загрузчик `WebServer`; его ошибки upload и
превышение 30-минутного лимита сейчас возвращаются как `400`, а не `408`.
Клиентам следует считать успешным только `201` и `done: true`, а текст
`error` использовать для диагностики, не для программной классификации.

## Ограничения и таймауты

- Передача идёт только на SD-карту, доступную Marlin, и только в её корень.
- Одновременно допускается один BFT-сеанс.
- На ESP8266 пауза поступления HTTP-данных более 5 секунд прерывает запрос;
  максимальная длительность upload — 30 минут.
- Клиент BFT поддерживает keepalive принтера во время ожидания HTTP-данных и
  периодически проверяет запись на SD. При потере файлового результата он
  не объявляет upload успешным и выходит из BFT только после безопасного
  восстановления. Если выход не подтверждён, UART остаётся зарезервированным.
- Внутреннее BFT-сжатие heatshrink согласуется с Marlin автоматически. Это
  деталь транспорта: HTTP-клиент всегда отправляет исходные байты файла.

## Отличие от прежнего ESP3D upload API

Не используйте для этого сценария старый `POST /upload?X-Filename=…` с raw
body или `POST /print`: эти маршруты не являются частью текущего
OctoPrint-совместимого BFT API. Для OctoPrint-клиента используйте только
`/api/version` и `/api/files/local`.
