# Клиент Marlin BFT в ESP3D

Клиент передаёт несжатые файлы по транспорту и файловому протоколу **0.1.0**. Проверка совместимости опирается на `sample_code/binary_stream.h`. Heatshrink и dummy-режим не реализованы; OPEN всегда содержит `dummy=0`, `compression=0`.

## HTTP-загрузка

Для текущей сборки ESP8266 с `COMMUNICATION_PROTOCOL RAW_SERIAL`:

```sh
curl --fail --data-binary @example.gcode \
  'http://esp3d.local/upload?X-Filename=example.gcode'
```

Тело — байты файла, требуется `Content-Length`; chunked encoding не поддерживается. Успешный результат: HTTP 200, `{"err":0}`. Ошибка: HTTP 400, `{"err":1}`; при включённой аутентификации без корректных credentials — HTTP 401. Это результат протокольной передачи, не проверка hash файла на SD.

Разрешено имя файла в корне SD, без `/`, `\`, префиксов диска и управляющих символов. Ограничение — минимум из 120 байт и `max_payload - 3`: при ответе `ss…,96,0.1.0` это 93 байта. Такое ограничение пути позволяет не использовать дефектный ABORT Marlin для подкаталогов. Существующий файл Marlin усекает при OPEN.

Перед загрузкой принтер должен быть свободен: OPEN в Marlin останавливает файловую печать. Клиент проверяет M115 и явный отказ возможностей BFT/SD_WRITE; автоматического определения всех видов печати нет. Отсутствие capability-строки допускается, поскольку расширенный отчёт Marlin может быть выключен.

HTTP-цикл читает только доступные TCP-байты и вызывает `idle()` между порциями. При простое QUERY отправляется каждые 3 секунды. Отсутствие HTTP-данных 5 секунд или общая длительность загрузки 30 минут завершает запрос ошибкой и запускает контролируемое прекращение передачи.

HTTP-маршрут реализован для ESP8266. На ESP32 доступны сервис клиента и интеграция UART, но HTTP-фасад BFT ещё не подключён.

## Жизненный цикл и ошибки

Один синхронный вызывающий код владеет операциями `begin`, `write`, `idle`, `finish`, `abort`. RX-callback только передаёт байты в защищённый буфер. UART резервируется до первого M115; обычные исходящие записи возвращают отказ до подтверждённого окончания сеанса.

Последовательность:

```text
M115 и его ответ → M28 B1, сообщение о переключении и ASCII ok
→ SYNC → QUERY → OPEN
→ WRITE → QUERY (повторяется для каждого блока)
→ QUERY → FILE/CLOSE → CONTROL/CLOSE
→ пауза 50 мс → M115 и его ответ → освобождение UART
```

QUERY после WRITE служит границей обработки: Marlin отправляет ACK до записи на SD, а файловая ошибка должна предшествовать ответу следующего QUERY. Ошибка сохраняется до конца передачи, включая cleanup. За это клиент платит дополнительным обменом QUERY на каждый блок.

По `rs<n>` повторяется сохранённый пакет с тем же номером, если `n` — текущий неподтверждённый номер. На один пакет допускаются два повтора, обычное ожидание ACK — 1 секунда, файлового результата — до 5 секунд после отправки последней попытки. Частичные записи UART досылаются; ограничиваются отсутствие прогресса и общее время отправки.

В предоставленном Marlin повтор номера 255 не распознаётся, а тело дубликата сканируется на `AD B5`. Поэтому при таймауте ACK для номера 255 или тела с таким token клиент **прерывает загрузку**, не выполняя небезопасный повтор. Явный `rs` текущего номера допускает повтор, поскольку сообщает, что пакет ещё не принят. CONTROL/CLOSE при потере ACK также не повторяется вслепую: принтер уже мог вернуться к ASCII.

`abort()` возвращает `true`, только если клиент подтвердил необходимое завершение и освободил UART. Для своей подтверждённой активной передачи он восстанавливает номер при необходимости, выполняет QUERY, FILE/ABORT и выход в ASCII. Перед SYNC после сбоя отправки даётся время истечь таймауту незавершённого пакета Marlin.

При потере результата OPEN/CLOSE, `busy`, переполнении RX, истечении срока владения файлом или неподтверждённом выходе состояние может остаться неопределённым. Тогда `abort()` возвращает `false`, UART остаётся зарезервированным, новые HTTP-загрузки отклоняются. Клиент не удаляет файл «на всякий случай» и не объявляет успех. Для возврата в работу требуется восстановить известное ASCII-состояние принтера и перезапустить ESP; при аппаратном восстановлении обычно перезапускают оба устройства. Наличие и содержимое файла после такой ошибки следует проверить отдельно.

## Автоматические проверки

```sh
python3 tools/bft/tests/run.py
```

Нужны Python 3 и C++17-компилятор (`g++` или `CXX`). Скрипт использует временный каталог, компилирует настоящие исходники клиента и приёмник из `sample_code`, заменяя UART, часы и SD. Сжатие в тестовом приёмнике отключено. Отдельно проверяются реальные методы резервирования и записи UART из `serial_service.cpp`.

Проверки охватывают 1024 контрольных пакета, произвольные байты, пустой файл, повторный сеанс, wraparound номера и часов, частичные UART-записи, фрагментацию ответов, потерю ACK и файловых результатов, ошибки SD, переполнение RX, длинные диагностики, keepalive и исключение конкурирующих записей. Полная HTTP-сессия, многозадачность на реальном ESP32 и физические ошибки SD требуют аппаратных испытаний.
