# Клиент Marlin BFT в ESP3D

Клиент передаёт файлы по транспорту и файловому протоколу **0.1.0**. Если QUERY сообщает `compression:heatshrink,8,4`, клиент включает сжатие и отправляет OPEN с `compression=1`. При других параметрах или отсутствии поддержки сжатия используется `compression=0`. Dummy-режим не реализован; `dummy=0` всегда.

Heatshrink encoder использует только статическую память: окно 256 байт, максимальная длина совпадения 16 байт, индекс включён. Состояние encoder занимает около 1,6 КБ RAM; выходной буфер на стеке — 128 байт. Динамическое выделение памяти в конфигурации библиотеки запрещено проверкой компиляции. В прошивку из каталога heatshrink собирается только encoder, без декодера, консольной утилиты и тестов.

Весь файл сжимается одним потоком с сохранением истории между вызовами `write()`. Перед CLOSE метод `finish()` выгружает оставшиеся сжатые байты, включая последний неполный байт. Повтор UART-пакета использует уже сохранённые сжатые данные. Каждый новый сеанс сбрасывает encoder; QUERY во время передачи не меняет выбранный режим. Размер входного буфера декодера Marlin (32 байта) не ограничивает размер WRITE-пакета.

## HTTP-загрузка

Актуальный HTTP-интерфейс BFT использует совместимые с OctoPrint маршруты
`GET /api/version` и `POST /api/files/local` с `multipart/form-data`.
Полный контракт запроса, ответы, ограничения и замечание по безопасности

## Жизненный цикл и ошибки

Один синхронный вызывающий код владеет операциями `begin`, `write`, `idle`, `finish`, `abort`. RX-callback только передаёт байты в защищённый буфер. Во время BFT обычные исходящие записи в UART отклоняются. После подтверждённого CONTROL/CLOSE UART освобождается даже при потере ответа на заключительный M115; сама загрузка в таком случае считается ошибочной.

Последовательность:

```text
M115 и его ответ → M28 B1, сообщение о переключении и ASCII ok
→ SYNC → QUERY → OPEN
→ WRITE → периодический QUERY (не реже одного на 4 KiB BFT-payload)
→ QUERY → FILE/CLOSE → CONTROL/CLOSE
→ пауза 100 мс → M115 и его ответ (при необходимости повтор) → освобождение UART
```

QUERY после WRITE служит границей обработки: Marlin отправляет ACK до записи на SD, а файловая ошибка должна предшествовать ответу следующего QUERY. Ошибка сохраняется до конца передачи, включая cleanup. Клиент разбирает ошибки перед каждым следующим пакетом, но делает строгий QUERY-барьер раз в 4 KiB BFT-payload и обязательно перед `FILE/CLOSE`; это убирает почти половину UART-обменов при обычном лимите Marlin 96 байт.

По `rs<n>` повторяется сохранённый пакет с тем же номером, если `n` — текущий неподтверждённый номер. На один пакет допускаются два повтора, обычное ожидание ACK — 1 секунда. Результат QUERY ожидается до 5 секунд; если ACK пришёл, а строка версии потеряна, отправляется один новый QUERY с новым номером. Он не меняет файл и не повторяет WRITE. Результат OPEN/CLOSE/ABORT ожидается до 30 секунд после отправки последней попытки. Частичные записи UART досылаются; ограничиваются отсутствие прогресса и общее время отправки.

В предоставленном Marlin повтор номера 255 не распознаётся, а тело дубликата сканируется на `AD B5`. Поэтому при таймауте ACK для номера 255 или тела с таким token клиент не повторяет пакет вслепую: SYNC сообщает текущий номер Marlin и позволяет определить, был ли пакет принят. Явный `rs` текущего номера допускает повтор, поскольку сообщает, что пакет ещё не принят. CONTROL/CLOSE при потере ACK также не повторяется вслепую: принтер уже мог вернуться к ASCII.

SYNC можно повторить без записи данных на SD. При потере запроса или ответа клиент отправляет до трёх SYNC в пределах пяти секунд; между ними проходит более 500 мс, чтобы приёмник Marlin успел завершить неполный кадр. Если ответа нет, ошибка указывает этап (`entry` или `packet recovery`), а для восстановления пакета также его тип и номер.

`abort()` возвращает `true`, только если клиент подтвердил необходимое завершение и освободил UART. Для своей подтверждённой активной передачи он восстанавливает номер при необходимости, выполняет QUERY, FILE/ABORT и выход в ASCII. Перед SYNC после сбоя отправки даётся время истечь таймауту незавершённого пакета Marlin.

При потере файлового результата клиент делает QUERY как границу обработки, ждёт истечения файлового тайм-аута Marlin и выходит из бинарного режима без FILE/ABORT: уже завершённый файл не удаляется. Успех загрузки при этом не объявляется. При `busy`, переполнении RX, истечении срока владения файлом или неподтверждённом CONTROL/CLOSE состояние может остаться неопределённым; тогда UART остаётся зарезервированным. Для возврата в работу обычно перезапускают принтер и ESP. Наличие и содержимое файла после ошибки следует проверить отдельно.

## Автоматические проверки

```sh
python3 tools/bft/tests/run.py --marlin-src /path/to/Marlin/src
```

Нужны Python 3, C99-компилятор (`gcc` или `CC`), C++17-компилятор (`g++` или `CXX`) и `nm`. Параметр `--marlin-src` указывает на исходники проверяемого Marlin с `feature/binary_stream.h` и `libs/heatshrink/heatshrink_decoder.cpp`. Скрипт использует временный каталог, компилирует настоящие исходники клиента, encoder и приёмник с декодером Marlin, заменяя UART, часы и SD. Проверяется отсутствие ссылок на функции динамического выделения памяти в объектном файле encoder. Отдельно проверяются реальные методы резервирования и записи UART из `serial_service.cpp`.

Проверки сжатия сравнивают распакованные байты с исходным файлом: фрагментированный ввод, пустой и короткий файлы, несжимаемые данные, завершение потока, повтор пакета, abort и новый сеанс, ошибки SD, keepalive и fallback при несовместимых параметрах.

Проверки охватывают 1024 контрольных пакета, произвольные байты, пустой файл, повторный сеанс, wraparound номера и часов, частичные UART-записи, фрагментацию ответов, потерю ACK и файловых результатов, ошибки SD, переполнение RX, длинные диагностики, keepalive и исключение конкурирующих записей. Полная HTTP-сессия, многозадачность на реальном ESP32 и физические ошибки SD требуют аппаратных испытаний.
