# Серия LinkedIn-постов: от ESP-01 и MKS к Marlin BFT в ESP3D

Ниже — четыре самостоятельных коротких поста. Их можно публиковать по одному;
в конце каждого есть переход к следующей теме.

---

## Пост 1. Wi-Fi для 3D-принтера — это не только «подключить ESP»

Я хотел добавить 3D-принтеру Wi-Fi так, чтобы подключение можно было настроить
удобно — в идеале через интерфейс самого принтера. На первый взгляд задача
кажется простой: взять OctoPrint или Klipper, подключить одноплатный компьютер
и отправлять G-code по сети.

Но у этого подхода есть цена. Одноплатник долго загружается, резкое отключение
питания может оставить систему в неконсистентном состоянии, а начальная
настройка нередко требует UART-адаптера, редактирования файлов на SD-карте или
подключения клавиатуры и монитора.

Поэтому я начал смотреть в сторону ESP3D: компактный ESP-модуль, привычная
прошивка принтера и меньше внешних компонентов. Однако в ESP3D v3 стандартную
загрузку файлов на SD-карту принтера уже убрали. Web-интерфейс и Wi-Fi есть, но
удобного надёжного пути положить G-code на SD принтера — нет.

Так задача «добавить Wi-Fi» неожиданно превратилась в задачу передачи файлов по
UART. Сначала я попробовал MKS File Transfer на маленьких ESP-01, затем понял,
что стабилизировать этот путь будет сложнее, чем построить новый.

В следующем посте — почему MKS-протокол оказался плохой основой для такой
интеграции.

## Пост 2. Почему я не стал стабилизировать MKS File Transfer

Первый прототип я собрал на ESP-01: компактные модули давно лежали без дела и
идеально подходили для быстрого эксперимента. Но MKS File Transfer быстро
показал, что совместимость на уровне «оно подключается» ещё не означает
надёжную архитектуру.

Протокол рассчитывает на два дополнительных сигнала между MCU и ESP:
`mcu_ready` и `esp_requests`. На используемых платах эти линии находятся на
разъёме LCD. То есть штатный дисплей и ESP3D нельзя было использовать
одновременно.

Чтобы провести эксперимент, пришлось изменить Marlin для работы без этих
сигналов и отвязать MKS File Transfer от графической библиотеки, от которой
зависела его реализация. Но и после этого оставались фундаментальные проблемы:

- перед началом передачи UART переключается на `1 958 400` бод;
- протокол в основном проверяет длину данных, но не даёт полноценной коррекции
  ошибок;
- на практике возникали ошибки передачи и переполнения буфера;
- upload шёл по HTTP-порту 80, а запуск файла требовал отдельного telnet-сеанса
  на нестандартном порту 8080.

Последний пункт особенно важен: слайсеру приходится реализовывать два разных
сценария, а пользователю сложнее понять, где именно произошёл сбой.

Я решил не наращивать workaround’ы вокруг MKS, а перейти к BFT — бинарному
протоколу, который уже предусмотрен в Marlin.

В следующем посте — что потребовалось, чтобы BFT был не просто быстрым, а
безопасным при реальных ошибках UART и SD-карты.

## Пост 3. Быстрый протокол бесполезен, если он не переживает потерю ACK

Marlin Binary File Transfer (BFT) решает ключевую проблему обычной G-code
загрузки: файл передаётся бинарным потоком, а не тысячами текстовых команд.
Но после `M28 B1` принтер переключается из ASCII-режима в бинарный. Любой
случайный G-code в UART с этого момента способен повредить передачу.

Поэтому реализация BFT в ESP3D строится как явная машина состояний:

```text
M115 → M28 B1 → SYNC → QUERY → OPEN → WRITE → CLOSE → ASCII
```

Во время сеанса UART эксклюзивно резервируется. Команды из HTTP и WebSocket не
«притворяются успешными», а получают `409 Conflict`.

Самая сложная часть — потерянный ACK. Безусловно повторить пакет нельзя:
Marlin мог принять первый экземпляр, и повтор продублирует данные в файле.
Вместо этого клиент использует `SYNC` как точку восстановления. Номер
последовательности Marlin позволяет понять, был ли пакет принят, или его можно
безопасно отправить снова.

Есть и другой нюанс: ACK пакета не обязательно означает, что SD-карта уже
записала данные. Поэтому клиент периодически отправляет `QUERY` как барьер
обработки и обязательно проверяет состояние перед закрытием файла.

При поддержке Marlin автоматически включается потоковое сжатие
`heatshrink,8,4`. Encoder работает со статической памятью — особенно важно для
ESP8266, где heap и стек нельзя считать бесконечными ресурсами.

совместимым с OctoPrint.

## Пост 4. От двух портов MKS к одному OctoPrint-совместимому API

После реализации BFT я отказался от MKS-схемы «HTTP upload на 80 + telnet для
печати на 8080». Вместо неё в ESP3D появился минимальный API, понятный
OctoPrint-клиентам и слайсерам:

- `GET /api/version` — обнаружение совместимого host;
- `POST /api/files/local` — загрузка одного файла как `multipart/form-data`;
- поле `print=true` — запуск печати после успешной передачи.

Файл не накапливается во flash или в RAM ESP3D: multipart body потоково
разбирается и сразу передаётся в Marlin BFT. Это важно для ESP8266. Для него
multipart parser и буферы вынесены из маленького continuation stack; на ESP32
используется streaming upload API `WebServer`.

После upload-and-print ESP3D по очереди выполняет `M21`, `M23 <filename>` и
`M24`, ожидая ответ на каждую команду. Так `ok` от монтирования SD нельзя
ошибочно принять за подтверждение выбора файла.

Для проверки я сделал host-side стенд: клиент ESP3D компилируется вместе с
реальным Marlin receiver. Проверяются фрагментация ввода, частичные
UART-записи, сжатие, ошибки SD, повтор пакетов, потеря ACK, keepalive, abort и
восстановление сеанса.

Главный вывод: в embedded-разработке хороший API начинается не с endpoint, а с
чёткой модели того, что означает успешный ответ. Здесь HTTP `201` означает не
«байты ушли в UART», а подтверждённое завершение BFT-загрузки.
